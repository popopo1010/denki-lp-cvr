### 3. Meta広告の着地7本の余白（#126）

全60本E2Eで発覚（953/967）。**今回の変更による退行ではなく以前からの不具合**。

原因は `assets/css/meta-short-lp.css:103` が入力ステップでヘッダーを `display:none`
にしていること。共通 critical CSS のアプリ内ブラウザ用の上余白 `64px` は
「先頭要素 ≒ 余白 + ヘッダー36px = 100px」を前提に決めた値（2026-08-29 に 96px から
下げた経緯）なので、ヘッダーを隠すと先頭要素が 64px に来る＝LINEのバー（実測83px）の
裏に沈む。**CLAUDE.md 頻出バグ⑤の再発が、一番広告費をかけている着地で起きていた。**

修正は「隠している側で36pxを埋め戻す」。共通CSSの 64px には触らない。

```css
html.dk-inapp.dk-ios body.meta-short-lp.lp-form-step .js-page-body { padding-top: 100px !important; }
```

反映後、全60本E2Eは **967/967**（953→967 に回復）。

## 本番未反映（判断待ち #1）

### FV画像(LCP)の二重ダウンロード（`f47e546`）

ページ実測でLPごとの転送量を出して発見。DPRを振って再現した：

```
修正前  DPR1  21KB（-sp のみ）
        DPR2  84KB（テーマ側960w 63KB ＋ -sp 21KB）
        DPR3  84KB（同上）
修正後  DPR1/2/3 すべて 21KB
```

iPhoneは全機種DPR2〜3、Androidも大半が2.6〜3なので、**実質すべてのスマホで
LCP画像を4倍の重さで取っていた**。

原因は、preload の候補選択が `imagesizes` に **DPRを掛けた実ピクセル幅**で行われること。
390px × DPR2 = 780px を要求するため 960w が選ばれる一方、`<picture>` は
`media="(max-width:767px)"` で -sp を選ぶ。両者が食い違って2枚落ちる。
PR #118 が別系統で直したのと同じ罠。

修正は preload を picture と同じ `media` で分けること（13ファイル）。あわせて
自前LP 10本にはモバイル用 -sp 画像自体が無かったので共有assetsから持ち込んだ
（220KB → 178KB / 272KB → 173KB）。

**記録**：最初は `imagesrcset` 方式で実装したが、実測すると 63+21=84KB と逆に重くなった。
食い違いを自分で作っていた。**measureしていなければ「最適化した」と報告して悪化させていた。**

## 今日踏んだ運用の教訓

- **パイプの後ろの `$?` はパイプ最後のコマンドの終了コード**。`release-pre-check.sh` を
  `| tail` に通して `$?` を読み、本番HTTP検証（実際は egress 遮断で exit 56）を
  「通った」と誤報告した。終了コードは直接受けて確認する。
- **YAMLのblock scalar内で、行継続 `\` の途中にコメントを置いてはいけない**。bash は
  行を連結してからトークン化するので `#` 以降が全部消え、rsync の除外指定と
  転送元・転送先ごと落ちる（デプロイが壊れる書き方だった）。
- **E2Eの結果は実行途中のログで判断しない**。`--- N/M passed ---` の最終行を見る。
  途中経過を見て「失敗0」と報告し、実際は14件失敗していた。

オーナーの指示「メインで使っているものとその他で分ける」を、感覚ではなく
**広告のリードログ**で決めた。Zoho商談の直近200件（2026-07-19〜08-31）をLP別に集計：

```

sekoukanri 系    0件   ← 出稿停止中。近く再開する（オーナー確認済み）
```

`marketing_channel` も全部 電気工事士 の出稿だった
（Google `014_denki_top_of_page` の各KW、Meta/IG の `暑さの中の電気工事士` `denkovlog` 系）。

実装は `scripts/lp-tiers.json` + `lp-tiers.mjs`。**ページの列挙は持たない**——
同じ `_lp` を名乗るミラーが root / WPLP / 自前LP / dk_lp にあるので、
列挙するとミラー追加のたびに漏れる。各HTMLの `window.__LP_ID` を走査して拾う。

- `node scripts/e2e-lp-flow-local.mjs --tier main` / `--tier rest`
- ci.yml は ①メインを毎回・②その他をPRのときだけ、別ステップで
- 解決結果が0本なら落とす（対象が空なのに「全部通った」に見える事故を防ぐ）

## `denkikouji-trust` が本家の数字に混ざっていた

テストLPが `window.__LP_ID="denkikouji"` を名乗っており、送信が本家 `/denkikouji/` と
区別できなかった。Zoho商談・シート・Slack通知・GTMの `lp_slug` すべてで混ざる。
**混ざったことはあとから一覧で拾えない**ので、静的に止めることにした。

分離にあたって芋づるで2つ直した：

1. `thanks-license-profiles.json` の `denki_lp.lp_slugs` に追加。ここに無いと
   このLPからの登録者だけ資格別サンクスが既定にフォールバックする
   （プロファイルは実行時fetchなのでビルド不要）
2. `generate-lp-thanks-redirects.mjs` が、既に転送ページがあると無条件に `continue` していた。
   つまり **`__LP_ID` を変えても `/thanks/` は古い `lp=` を送り続ける**。今回まさに踏んだ。
   中身が現在の `__LP_ID` と食い違っていたら書き直すようにした（一致なら書かない＝差分なし）

番人は `check-form-invariants.mjs` に追加。判定は
「同じ `__LP_ID` を名乗るページは同じLPのミラーでなければならない＝ディレクトリ名が揃っていること」。
`dk_lp/sekokanri`（綴り違い）だけ既知の別名として許可している。
meta-lp のように意図して別IDを持つページは、そもそも衝突しないので対象外。
