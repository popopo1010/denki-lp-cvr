## 4. 全体最適案（前提ごと変える場合の優先順）

「WordPressを使っている」が、**LPの描画にWordPressはもう関与していない**（2026-08-23〜 全LPが静的HTML＋
`theme-snapshot.css`）。残っている依存は次の3点で、速度に効くのは (a) だけ。

- (a) **Xserver の TTFB**（最大の残余）: ローカルで LCP 1.4s に対し本番PSIは ≈90。文書の TTFB がそのまま LCP に乗る。
  → **Cloudflare（無料プラン）を前段に置く**: DNSを切り替えるだけで、静的アセットのエッジキャッシュ、brotli、HTTP/3、
  TLS早期終端が得られる。HTML は `no-cache` のまま（オリジン再検証）で運用ルールを変えずに済む。
  注意点: WAF/キャッシュルールで `/denki-lp-cvr-stg/` は noindex ヘッダを通す・`booking-slots.json` は
  キャッシュしない（既に no-cache）。**オーナーのDNS操作が必要**なので提案止まり。
- (b) **WPテーマ画像の同梱**: FVのPC用バナー・2択ボタンのアイコン・step01の資格アイコン・クマ
  （`/wp-content/themes/original-thema/assets/img/*`）は同一オリジンだが WP 側の配信設定（キャッシュ期間）が
  こちらの `.htaccess` の外にあり、テーマ更新でパスが変わると壊れる。`assets/img/theme/` にコピーして参照を
  切り替えれば、LPの描画に必要なものが全部リポジトリ管理下（immutable キャッシュ・`check-local-refs` の対象）になる。
  サンドボックスからは WAF で取得できないため、`Snapshot WP theme CSS` と同じくランナーで取得する手順が要る。
- (c) `/terms` `/privacypolicy` は WP の固定ページ（LP外・別タブ）。速度には無関係。

コード側で**やらないと決めたこと**（計測済み）:

- **CSSのHTMLインライン化**: レンダーブロック要求は 0 になるが、FCP 903→1,020ms に悪化、LCP 不変（1.40s）。
  LCP は preload 済みのFV画像で決まり、HTML が 7.4→14.6KB に太る分だけ初回描画が遅れる。
- **cvr-boost-*.css の purge**: 削減 3% 未満。
- **FV画像の再圧縮**: 既に q≈72 相当。q60 でも −1.3KB。deploy の `optimize-images.mjs`（q80）は「元より大きくなる」ため据え置き。
  Lighthouse の「6KB 削減可」は当たらない。
- **shine アニメーション**: アイドル3秒で style/layout 再計算 +1ms 未満（compositor）。
- **GTM lazy（操作 or 8秒）／CSS同期読み込み／FV固定高さ**: 2026-08-19 の判断のまま正しい。触らない。

## 4b. サーバー側（TTFB）を詰めるときの手順（2026-09-04 オーナー質問への回答）

**先に測る（10分・DNSを触らない）**。PSI の「実際のユーザー環境」タブの TTFB（CrUX）と、WebPageTest（Tokyo）の
`denkikouji/` を見る。ローカルの LCP 1.4s と本番PSI≈90 の差が「ラボの計測地点が遠い」だけなら、
実ユーザーの TTFB は既に合格域で、下の (1) の価値は HTTP/3 とアセットのエッジ配信ぶんに縮む。
CrUX の TTFB が 800ms を超えていれば本命として進める。

| 優先 | 手段 | 効くもの | 代償・注意 |
|---|---|---|---|
| 1 | **Cloudflare 無料プランを前段に**（DNSをプロキシ化するだけ。デプロイ手順は不変） | TLS終端・HTTP/3 が東京/大阪エッジ、`assets/*` の immutable アセットはエッジ配信。HTML は `no-cache` のままでも、**Edge TTL 5〜10分／Browser TTL は origin 尊重**の Cache Rule を `/denki-lp-cvr/*` に当てれば HTML の TTFB もエッジになる | ①deploy.yml の rsync 後に Cloudflare API で `/denki-lp-cvr/*` をパージ（Secret: `CF_API_TOKEN` `CF_ZONE_ID`）。パージが無いと「?v= を上げたのに効かない」の再来 ②同一ドメインの WordPress（`/wp-admin` `/wp-login.php` `/wp-json`・`wordpress_logged_in` Cookie）はキャッシュ除外 ③STG `/denki-lp-cvr-stg/*` は `X-Robots-Tag: noindex` を通すこと（キャッシュ除外が無難）④Xserver 側で実IP復元（Cloudflare の IP を WAF が誤検知しないか STG で確認）⑤SSL は Full(strict)。効いたかは STG検証ログの `cf-cache-status: HIT` と `content-encoding: br` で見る |
| 2 | **Xserver の設定だけ**（DNS不要・即日） | Xアクセラレータ Ver.2（静的ファイルのサーバー側キャッシュ）、HTTP/2 有効、`mod_brotli` が無ければ gzip のまま | 効果は小さい（オリジンの Apache 処理が数十ms減る程度）。まず STG検証ログの `content-encoding` で gzip/brotli が本当に出ているかを見る。出ていなければ `.htaccess` の IfModule が空振りしている＝ここを直すのが先 |
| 3 | **LPだけ静的ホストへ**（Cloudflare Pages / Netlify を `/denki-lp-cvr/*` にルーティング） | オリジン依存ゼロ。HTML までエッジ | 広告のリンク先URLは不変にできる（同一ドメインのパスルート）が、デプロイ経路（rsync→Pages）・STG（プレビュー）・`.htaccess`（no-cache/リダイレクト）の全面移行になる。(1) の後、オリジンが依然ボトルネックのときだけ |

やらないこと: ドメイン変更（広告URL・計測・Cookie が全部動く）、Xserver のプラン変更（TTFB は変わらない）。

→ 実施手順（段階・設定値・確認・戻し方）は **`docs/cloudflare-setup.md`**。リポジトリ側の準備（deploy.yml のパージ・probe のヘッダ表示）は同日に入れてあり、Secret 未設定のあいだは何も動かない。

## 5. 失敗メモ（つまずいたこと・二度目を防ぐ）

1. **Playwright の CSS カバレッジ（`page.coverage.startCSSCoverage` と CDP `CSS.startRuleUsageTracking`）は
   このヘッドレス構成で 0% / 空を返した**。未使用CSSの見積もりは PurgeCSS のドライラン（残った/落ちた規則の一覧）で行い、
   正しさは実ブラウザ比較で担保する、が正解。
2. **ピクセル比較は白黒つかない**。偽差分が3種類出た: ①ネイティブ `select` の矢印が 8px だけ違う（再試行でも同じ）
   ②sticky CTA がスクロール位置で動き、エラー表示直後は app.js のキーボードナッジが最長1.5秒スクロールし続ける
   ③施工管理 step06 で入力状態がタイミングでズレる。→ 判定は **全要素の computedStyle 一致**に変更。スクショは参考。
3. **携帯番号を 11 桁入れると app.js が約1.1秒後に自動送信して thanks へ遷移する**（`step-last-button.click()`）。
   検証ツールが遷移して落ちた。歩行ツールでは番号を途中で止める／`/thanks` を 204 で握る。`abort` だと
   エラーページへ遷移して context が壊れる。
4. **PurgeCSS の `variables: true` は `:root` のCSS変数（`--sm` `--tab` 等）を落とす**。描画は変わらないが
   computedStyle が正本と一致しなくなる。`variables: false` で保持（数十バイト）。
5. **CSS変数の computedStyle 列挙順は宣言順で変わる**（`--lg`/`--xl` が入れ替わる）。比較はプロパティ名でソートしてから。
6. **esbuild の minify は `/*!` のリーガルコメントを残す**ので、テーマの webpack ビルド情報コメント（約500B）が
   生成物に残った。ビルド時に自前バナー以外の `/*!` を落とす。
7. **サンドボックスから本番/STG の HTTP ヘッダは取れない**（プロキシが CONNECT を 403）。圧縮・キャッシュの実効確認は
   deploy.yml の STG検証に出力を足して、GitHub Actions のログで見る。
8. **ローカル Lighthouse は TTFB≈0 で perf 100 が床**。本番との差（TTFB）はローカルで再現しない。数値は相対比較にだけ使う。
11. **FVの `min-height: calc(100svh - 200px)` は、全機種で初期画面の下端に次セクション（体験談）の見出しが 74〜90px 覗く**
    （ヘッダーは 78〜94px しかない）。2026-06 から続いていた設計で、オーナーが施工管理LPの実機で気づいた。
    ローカルの E2E・visual-diff は「崩れていない」ことしか見ないので拾えない。`calc(100svh - 100px)` に変更
    （全機種で下端の 10〜26px 下に隠れる）。**「初期画面に何が入るか」は数値で測る**（`scratchpad` の fv-fold 計測: 360×640 / 390×844 / 390×740 / 430×932）。
12. **施工管理LPの step01 で「資格ボタンとCTAの間に余白 16px」を意図した規則が、同じ specificity の後続規則（`padding-top: 4px`）に
    上書きされて一度も効いていなかった**（オーナー実機「CTA近すぎ」）。同一セレクタの重複宣言は後勝ちなので、意図を書いたコメントが
    あっても効いているとは限らない。修正: 16px を1か所に集約し、短い画面（高さ660px以下）だけ 8px。**間隔は機種幅×高さで実測**
    （`scratchpad` の step01-gap 計測: 360×640 / 390×844 / 390×740 / 390×660 / 430×932 で CTA が初期画面内か）。
13. **キーボードでSTEP表示が沈む再発（真因）**: ナッジと 96px 余白が `html.dk-inapp` 限定で、dk-inapp は UA 検知
    （Instagram/FB/LINE/Messenger）でしか付かない。UA が Safari と同じ **SFSafariViewController**（Slack・X・メール等
    から開くブラウザ）では一度も動いていなかった。E2E も LINE UA だけで再現していたので緑のまま。
    修正: ナッジは全ブラウザで動かし、閾値だけ `BAR()`（dk-inapp=96 / それ以外=12）。番人と Safari UA の E2E を追加。
    教訓: UA 検知に依存した対策は、UA で見分けられないブラウザで必ず再発する。
10. **deploy.yml の中のシェルを Python の三重引用符で編集して、閉じ引用符を食った**（`echo "--- 求人カードの資産 ---` → STG run #511 が Verify で
    "unexpected EOF"。rsync 後なので STG の中身は更新済みだった）。差分は目で見ていたのに気づけなかった。以後は
    `scripts/check-workflow-shell.py`（全ワークフローの `run:` を `bash -n`）が ci.yml と release-pre-check で止める。
    同じ番人が、以前からあった `snapshot-theme-css.yml` の `gh pr create ... \\` （YAML内で `\\` は2文字のバックスラッシュ＝行継続にならず
    次行の `|| echo` が構文エラー）も拾った。テーマ差分が出た週にPR作成だけ失敗する潜在バグだった。
9. `scripts/check-asset-versions.mjs --update` を、HTML編集・生成物の更新の**両方の後**に流す（生成物の中身が変わるたびに台帳の
   ハッシュが変わる。順番を誤ると「上げ忘れ」として落ちる）。

挟まっていた。CTA は `position:sticky; bottom:0` なので、キーボードが開いた短いビューポートでは CTA が下端に張り付き、
間のバッジ＋焦り文だけが中空に浮いて見える（実機スクショの赤丸）。

- denkikouji の step06 を sekoukanri と同じ構造にした: 入力欄 → 安心文 → 焦り文 → CTA → 満足度（1行テキスト
  `.cvr-cta-proof`）→ 同意文。枠つきバッジ（`.cvr-cta-proof--badge`）は主力LPから外した（v3〜v6 / trust は別ファイルのまま）。
- **両LPで、CTAの下 120px の空白を詰めた**: テーマの `.p-step06 .c-nextLink{margin:60px 0 120px}` の下余白が残っていて、
  CTA直下に置いた満足度・同意文が 120px 離れて浮いていた（sekoukanri は以前からこの状態。sticky の CTA に隠れて
  気づきにくかった）。`body.lp-input-step #step06 .c-nextLink{margin-bottom:8px}` を cvr-boost 両方に追加。
  実測（390×844）: CTA 下端 359px → 満足度 367px → 同意文 387〜413px（修正前は満足度 479px）。

### 8b. step04 の都道府県 select で矢印が二重（オーナー実機指摘「枠内の記号がかぶってる」）

`<select id="pref">` は inline の `-webkit-appearance:menulist`（d351b76 由来）で OS 標準の矢印（iOS17 は「⌃⌄」）を出すのに、
テーマの `.c-select-box::after`（赤▼・right:24px）が残っていて二重に描かれ、位置もズレて重なって見えた。本番でも同じ
（theme-snapshot / theme-lp どちらも同じ規則）。標準の矢印に統一し、`#step04 .c-select-box::after/::before{display:none}` を
両 cvr-boost に追加（denkikouji `?v20260904f` / sekoukanri `?v20260904g`）。
同じ inline 指定は meta-lp / nenshu-shindan 系 15本（`cvr-boost.css` / `cvr-boost-v2.css`）にもあるが今回の対象外（要フォロー）。

### 8c. E2E のキーボード競合再現が「文書の高さ」に依存していた（失敗メモ）

step06 の下余白 120px を詰めたら、`e2e-lp-flow-local` の Safari レースが denkikouji だけ落ちた（`headTop=80→7px`）。
390×360 の疑似キーボードビューポートで「入力欄を最上部へ」押し下げるのに必要なスクロール余地が無くなり、押し下げが 73px で
頭打ち＝見出しが 7px（BAR 12px − MIN_MOVE 8px の不感帯）に残っただけで、ナッジは設計どおり動いていた。しかもこの状態では
**ナッジを無効にしても同じ 7px** になり、退行を検知できない。`keyboardRace` が `body{padding-bottom:800px}` を一時的に足して
余地を固定するようにした（実機はキーボード分だけ必ず余地がある）。教訓: レイアウトを詰めたら、そのレイアウトに依存する
再現条件（スクロール余地・ビューポート高）を持つテストが**空振りで緑にならないか**も見る。
