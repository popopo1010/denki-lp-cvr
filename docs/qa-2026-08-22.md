# 品質チェック結果（2026-08-22）

対象: `denki-lp-cvr` 全体（LP 60本以上 / 共有JS・CSS / 生成スクリプト / CI / リリース手順）

結論から言うと、**個々のLPの作りは良く、既存チェック（禁止コピー・クマ初期位置・参照切れ・thanks-v2）はすべて緑**だった。
問題が出たのは「LPが1本ではなく60本ある」ことに起因する場所——**直したはずの修正が一部のLPにだけ当たっていない**、
**修正を止める仕組みが本番デプロイ時にしか動いていない**、の2点に集中していた。

## 1c. 再確認: step05で上部が隠れる件の切り分け（2026-08-23）

E2Eドライバを「実ユーザーと同じく入力し終えたら欄を離れる(blur)」挙動に直したところ、
**step05で上部見出しが画面外に出る**判定が7本のLPで出た（headTop -53〜-139px）。
`scrollTo`/`scrollIntoView` を差し替えてスタックを取り、犯人を実測した結果:

- 入力を埋めただけでは動かない（headTop=110のまま）
- **全項目が埋まった状態で欄を離れた瞬間**に `moveIcon` が `.c-nextLink` を
  `scrollIntoView({block:"nearest"})` し、y=0 → 206 へスクロール（headTop -96）

これは「入力が揃ったらクマをCTAへ移動して次の操作へ誘導する」という**仕様どおりの動き**で、
CTAが背の高いステップの下端にあるため `nearest` でも下へ動く。CLAUDE.md が禁じているのは
`block:"center"`（中央寄せ）であって、この `nearest` 誘導は設計どおり。

→ **不具合だったのはE2Eの判定タイミング**。守るべき不変条件は
「**ステップに到達した瞬間**に上部（STEP表示・タイトル）が見えていること」であって、
「入力完了後にCTAへ誘導した後も見えていること」ではない。判定を到達時に限定した。

### 併せて直した実際の不備（原因ではないが誤り）

切り分けの過程で、`focus()` に `preventScroll` が付いていない箇所が複数あり、
`app-v2.js` には **`focus({ preventScroll: false })`** と、ブラウザ主導スクロールを
明示的に許可する書き方まで残っていた。上記の症状の原因ではなかったが、
CLAUDE.md の犯人クラス④そのものの書き方なので全実装で `preventScroll: true` に統一し、
`check-form-invariants.mjs` を「**focus() は必ず preventScroll 付き / preventScroll:false を書かない**」で固定した
（従来は「ファイル内のどこかに1つでも preventScroll があればOK」という緩い判定だった）。

## 1e. 「load前クリック」判定のフレーキー解消（2026-08-23）

全50本の掃引で `WPLP/sekoukanri` 系2本が「load前クリックがデッド」で落ちたが、
同じLP・同じコードで5回まわすと**落ちたり通ったりした＝テスト側の競合**だった
（構造も本番LPと同一で、どちらも `<script src="app.js" defer>`）。

原因は「`goto(waitUntil:"domcontentloaded")` の直後にクリック」がタイミング依存だったこと。
ローカル配信が速いと load 後にクリックしてしまい、逆に遅いとページ側の DOMContentLoaded
ハンドラより先にクリックしてしまう。**「load前」という前提自体が保証されていなかった。**

対策: 外部リソース（WPテーマCSS・画像）の中断を4秒遅らせて window load を保留させ、
`readyState !== "loading"` を待ってからクリックし、**クリック時点の readyState を結果に出す**。
`complete` になっていたら「検証できていない」と明示的に落とす（黙って通さない）。
→ `readyState=interactive` を実証した上で 22/22 パス。

## 1l. 【実機で発覚】キーボードを開くとSTEP表示がバー裏に沈んだまま（2026-08-23 オーナー報告）

実機確認の依頼に応えてオーナーがLINEアプリ内ブラウザで確認 → **denkikouji・sekoukanri両方のstep06で、
入力欄タップ後にSTEP表示・タイトル・「携帯番号」ラベルが上部バーの裏に隠れたまま**というスクショ2枚。
頻出バグ⑤の再々々発。**今日のデプロイによる退行ではない**（ナッジのコードは2026-07-08のPR #93から
バイト単位で無変更なことをgitで確認）。実機確認が初めて行われたことで可視化された。

### 原因は2段重ねだった

1. **ナッジが「300ms後に1回だけ」でiOSのレースに負ける**：iOSはキーボードのアニメーション完了時
   （〜1秒）に入力欄を最上部へ**もう一度**スクロールし直す。1回きりの補正はその前に走って空振りするか、
   走った後に上書きされる。**ヘッドレスで再現**：ビューポートをキーボード高（390×360）へ縮めてから、
   フォーカス後300ms超に入力欄を最上部へscrollToすると、`head.top=-81` のまま戻らない
   （通常ビューポートではページがスクロール不能で再現しないことも判明——過去のPlaywright検証が
   この症状を素通りさせてきた理由）。
2. **ガードが全か無かで、v2系・dk_lp系ではナッジが実質無効だった**：補正前の条件

## 1p. 【真因】同じページからの2件目以降が無言で消えていた（2026-08-23）

オーナーの「昨日から今日で3回テストして1回分しか出てこない」「Slackにも来ていない」
「電話番号は関係ないもので、氏名はSRなどアルファベット」という報告から特定。

### 何が起きていたか

送信ミラーの「1回だけ送る」判定が **1ページ読み込みにつき1回**（クロージャ内のboolean）だった。
そのため同じページから2件目以降を送ると、**検証も通り送信ボタンも押せるのに、
Zapierにも GASにも何も飛ばない**。Slack通知も出ないので気づけない。

実ブラウザで再現（送信先へは到達させず回数のみ計数）:

| | Zapier | GAS |
|---|---|---|
| 同一ページ 1件目 | 1 | 1 |
| 同一ページ 2件目（別人として送信） | **0** | **0** |

オーナーの「**むしろ3回目でいけた。フォームを変えたからかな**」という観察が決定的だった。
**別のLPを開く＝新しいページ＝JSの状態がリセット**され、そこで1件目扱いになって届いた。
症状（1/3しか届かない・ページを変えると復活する）と完全に一致する。

**氏名のアルファベット（SR等）は無関係**だった。6パターン（SR / S+R / sr / Test+Sr /
日本語 / 別番号）を実測し、すべて Zapier=1 GAS=1 で正常に送信されている。

### 対策

送信は**原則すべて通す**（同一人物の再送信も、別人の連続送信も届ける。オーナー方針）。
止めるのは「1タップで submit が二重発火した」事故だけなので、
**まったく同じ内容（電話+姓+名）が3秒以内に連続した場合のみ**2件目を捨てる。

実測での確認:

| シナリオ | 結果 |
|---|---|
| 同一内容を200msで二連打（1タップの二重発火） | 1件だけ送信 ✓ |
| 別人として続けて送信 | 2件とも送信 ✓ |

### 再発防止

`check-form-invariants` の検査を「送信済み判定をフォーム単位で持つ」から
**「再送信を止めない（短時間の二重発火のみ抑制）」**に変更。
`sentOnce` / `sentForms` / `sentKeys` のような**永続的に止める持ち方に戻したら落ちる**。

### GA4での裏取り

オーナーがGA4（denki-koji）のイベント一覧を確認 → **`lp_error` は0件**。
つまり 1o のDOM差し替え経路は**本番で一度も発生していない**。今回の消失は
すべてこの「1ページ1回」ガードによるもので、DOM差し替えとは無関係だった。

なお `form_step` / `lead_form_submit` / `lead_conversion` もGA4に出ていない
（出ているのは `form_start` / `form_submit` / `thanks_pageview` ＝GA4拡張計測）。
**GTMにカスタムイベントをGA4へ転送するタグが無い**と思われる。
ファネルを数字で追うなら、この配線が別途必要。

| フッターの規約リンクが 13px高 | 行の高さのまま | `min-height:44px`（Apple HIG / Material） |
| step06 の同意文リンクが 10〜12px高 | 同上 | **あえて24px（WCAG 2.5.8 の最低基準）にとどめる**。送信CTAの真横なので44pxまで広げると誤タップでLPから離脱する事故が増え、CVRを下げる。インライン要素の上下 padding は行送りを変えずに当たり判定だけ広げられる |
| 自前LP step01 の選択肢が 40px高（SE） | 1画面に収めるための圧縮 | 44px へ。CTAが画面外に出ていないことを実測で確認 |

### 【重要】横スクロールは「文書幅」で測ってはいけない

`document.documentElement.scrollWidth > 画面幅` で判定していたが、これは**誤検知する**。
Chromium のモバイルエミュレーションは、読み込み中に一瞬でも内容が画面幅を超えると
ICB(初期包含ブロック)を広げ、内容が収まっても**元に戻さない**。
その状態では `innerWidth` も `scrollWidth` も広がったままで、
実際には1pxも横に動かないページが「横スクロールあり」と報告される
（`/自前LP/denkikouji/` が全機種・全ステップでこれに当たり、
 最右の要素は 375px に収まっているのに文書幅だけ 409px だった）。

正しい測り方は**実際に動かしてみること**:

```js
const sx0 = window.scrollX;
window.scrollTo(vw * 3, window.scrollY);
const scrollableX = window.scrollX - sx0;   // 0 なら横スクロールしない
window.scrollTo(sx0, window.scrollY);
```

同じ理由で、要素を1つずつ `display:none` にして犯人を探す二分探索も
ICBが広がったままだと嘘の犯人を指す。**先に reflow を強制してから測る**こと。
