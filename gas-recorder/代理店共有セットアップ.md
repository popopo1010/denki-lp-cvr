# 候補者ステージの代理店共有（個人情報なし）

マーケ代理店に「どのチャネル／キャンペーンから来た候補者が、いま Zoho CRM のどのステージか」を
**随時（1時間ごと）自動更新**で共有する。**個人情報は一切渡さない**。
コードは `gas-recorder/agency-share.js`。

## 何を共有し、何を共有しないか

| 共有する | 共有しない |
| --- | --- |
| `lead_id`（不可逆ハッシュの匿名ID） | 氏名 |
| 送信日 / 送信月 | 電話番号 |
| LP名（denkikouji / sekoukanri など） | メールアドレス |
| マーケチャネル（例 `google/cpc｜014_denki_top｜KW: 電気工事士 求人`） | 生年月日 |
| `utm_source` / `utm_medium` / `utm_campaign` / `utm_content` / `utm_term` / `utm_id` | 郵便番号・都道府県・市区町村 |
| **逆オファーOK到達**（`✓` / 空欄） | 保有資格・経験・転職意欲 |
| LINE登録の有無 | IPアドレス・UA・送信時URL（`_page`）・**ステージ名そのもの** |

- `lead_id` は「商談ID＋ソルト」のSHA-256を12桁に切ったもの。**本人には戻せない**が、
  同じ候補者は常に同じIDになるので、代理店側で重複・再訪をカウントできる。
- 広告クリックID（`gclid` / `fbclid` 等）は既定で**共有しない**。オフラインCVの取り込みで
  必要になったら `agency-share.js` の `AGENCY_SHARE_INCLUDE_CLICK_IDS` を `true` にする。
- テスト送信は自動で除外される。判定は **`_test` 列を最優先**（`stg` / `param` / `pattern`。
  2026-08-30〜の運用でテスト行もシートに残るようになったため）＋ 旧行向けの推測判定
  （連番電話番号・プレースホルダー氏名）。STGや `?dk_test=1` からの本物らしい氏名・番号のテストは
  `_test` 列でしか捕まらない。

## 【重要】Zoho の画面・エクスポートは代理店に見せない

Zoho商談の **LP情報 `lp_info` には、2026-05以前のレコードを中心に氏名・電話番号・郵便番号が
そのまま入っている**（旧フローで作られた分。`名前：◯◯ / 電話番号：090…` の形式）。
ステージを見せたいからといって Zoho のビュー共有・CSVエクスポート・レポート共有をすると
**個人情報がそのまま渡る**。代理店に渡してよいのは下記の共有スプレッドシートだけ。

## なぜ別スプレッドシートなのか

Googleの共有権限は**ファイル単位**で、同じスプレッドシート内のタブごとには分けられない。
`form_submissions` を共有すると氏名・電話まで見えてしまうため、
**個人情報を落とした行だけを別ファイルに書き出し、そのファイルだけを代理店に渡す**。

## セットアップ（初回のみ・10分）

1. `clasp push -f` でコードを反映する（`gas-recorder/` で実行）
2. Apps Script エディタ → ⚙️ プロジェクトの設定 → スクリプトプロパティに設定する

   | プロパティ | 値 |
   | --- | --- |
   | `AGENCY_SHARE_SHEET_ID` | `1E-5W9gOFKjUbjxy2HIdK27Cu72-0HrI5NzexFPRFxJw` |

   そのうえでエディタから **`syncAgencyShare`** を実行すると、3つのタブが作られて中身が入る。
   匿名IDのソルト `AGENCY_SHARE_SALT` は初回実行時に自動生成される
   （**このソルトは変えない**。変えると過去の `lead_id` と繋がらなくなる）。

   > 別のスプレッドシートを使いたい場合は `AGENCY_SHARE_SHEET_ID` をそのシートのIDに
   > 差し替えるだけでよい（`setupAgencyShare` を実行すると新規作成もできる）。

   **共有するチャネルを絞りたい場合**（任意）:

   | プロパティ | 値 | 意味 |
   | --- | --- | --- |
   | `AGENCY_SHARE_UTM_SOURCE` | `google` | Google広告の行だけ共有。Meta(fb/ig)・自然流入は出さない |
   | | `google,fb` | GoogleとMeta |
   | | （未設定） | 全チャネル |

   Google広告は自動タグ設定で `utm_source` が付かず `gclid` だけ付くことがあるため、
   `google` 指定時は **`gclid`/`gbraid`/`wbraid` を持つ行も対象**に含める。
   絞り込みで落とした件数は実行ログと `凡例` タブに出る（黙って絞らない）。
3. **自動更新のトリガーを登録**する
   Apps Script エディタ → ⏰［トリガー］→ トリガーを追加
   - 実行する関数: `syncAgencyShare`
   - イベントのソース: 時間主導型 / 時間ベースのタイマー / **1時間おき**
   > コードからトリガーを作らないのは、`script.scriptapp` スコープの追加＝**再認可**が必要で、
   > 稼働中のフォーム受信エンドポイント（`doPost`）を止めうるため。
4. 共有シートを開き、代理店に **「閲覧者」で共有**する（編集権限は渡さない）
   - リンクを知っている全員に公開せず、**代理店の担当者アドレスを個別に指定**する
   - 「閲覧者がダウンロード・印刷・コピーできないようにする」は任意（オンでも中身は見える）

## シートの構成

| シート | 中身 |
| --- | --- |
| `候補者ステージ` | 1候補者1行の明細（1行目がヘッダー。ピボット・Looker Studio からそのまま読める） |
| `チャネル別サマリ` | 月 × `utm_source`/`utm_medium`/`utm_campaign` の 送信数・LINE登録数・逆オファーOK到達数と率 |
| `月別推移` | 月ごとの候補者数・LINE登録・逆オファーOK到達数と到達率、**単価** |
| `キャンペーン別到達率` | `utm_campaign` ごとの候補者数と **逆オファーOK到達数・到達率(%)・単価** |
| `KW別到達率` | `utm_term`（検索KW）ごとの同上。検索広告以外は `(なし)` にまとまる |
| `広告コスト入力` | **人が入力するタブ。自動更新で消えない唯一のタブ** |
| `凡例` | 各列・各タブの意味、対象チャネル、最終更新時刻 |

### 単価（CPA）の出し方

`広告コスト入力` タブに **年月 / キャンペーン / 広告費(円)** を入れると、
`月別推移` と `キャンペーン別到達率` に **候補者単価** と **逆オファーOK到達単価** が出る。

| 年月 (YYYY-MM) | キャンペーン (空欄=その月の全キャンペーン) | 広告費(円) | 粒度 |
| --- | --- | --- | --- |
| 2026-07 | 014_denki_top_of_page | 200000 | month |

- 列は**ヘッダー名で探す**ので、右に列（広告グループ・管理画面CV など）を足しても壊れない
- **`粒度` 列に注意**。広告管理画面から貼ると、同じ費用が `month` と `week` の両方で
  入っていることがある。全部足すと**二重計上**になるため、**年月ごとに粒度を1つだけ採用**する
  （`month` > `week` > `day` > 粒度なし の優先順）。除外した行数は実行ログに出る。
  （2026-09-01: month 8行 + week 302行が混在し、候補者単価が930,856円に化けた）
- キャンペーン名は**広告側の名称と一致**させる（`utm_campaign` と突き合わせる）。
  一致しないキャンペーンの費用は【全体】には乗るが、キャンペーン行には出ない
- 月別の単価だけ見たい場合はキャンペーン欄を空にして年月と費用だけ入れればよい
- 費用が空なら単価列は空欄になる（0除算しない）
- **KW別タブに単価は出さない**（KWごとの広告費は取得できないため）
- Google Ads の API を繋ぐようになったら、このタブを自動更新に差し替えるだけで単価計算はそのまま動く

### 逆オファーOK到達の判定（重要）

代理店に見せるのは **`08_逆オファーOK` まで到達したかどうかの1列だけ**。
それ以外のステージ名（`02_未通電` `27_ナーチャリング` `28_無効リード` 等）は**共有シートに出さない**。

- `✓` … 現在のステージが `08_逆オファーOK` 以上
- 空欄 … 未到達。**ただし「まだCRMに登録されていない（送信直後・連携エラー）」も空欄**になるため、
  厳密には「未到達 or 判定不能」
- `27_ナーチャリング` / `28_無効リード` は**番号が大きいが前進ではない**ので到達扱いにしない
  （`agencyShareStageRank` が rank 0 を返す）。ここを素直に数値比較すると無効リードが
  「到達」に化けて率が壊れる
- ステージ履歴はZohoから取っていないため、**一度到達してからナーチャリング/無効リードに戻った候補者は
  チェックが外れる**（＝実態よりやや低めに出る）。正確な「一度でも到達したか」には Stage 履歴の取得が必要

**別の段階も見たくなったら** `agency-share.js` の `AGENCY_SHARE_TARGET_RANK` を変える
（`04_HOT` なら 4、`21_内定` なら 21）。

### 到達率タブの読み方

各行の分母は「そのキャンペーン/KWの送信数」。先頭行は `【全体】`、以降は送信数の多い順。
列は 送信数 / LINE登録 / LINE登録率(%) / 逆オファーOK到達 / 逆オファーOK到達率(%)。

Looker Studio で見たい場合は、この共有スプレッドシートをデータソースにする
（元の `form_submissions` は**絶対に接続しない**）。

## 運用

- **更新タイミング**：1時間ごと。毎回まるごと作り直すので、Zohoでステージを動かせば次の実行で反映される。
- **手動で今すぐ更新**：エディタで `syncAgencyShare` を実行。
- **代理店が編集しても壊れない**：次回更新で上書きされる（＝手元のメモは別ファイルに書いてもらう）。
- **Zohoが一時的に落ちている場合**：行は書き出されるが、到達チェックが全て空欄になる。
  戻り値とSlackのエラーチャンネルに理由が出るので、`※Zoho取得エラー` が出た回の数字は使わない。
- **除外した件数は必ずログに出る**（テスト送信 / 電話番号なし / チャネル絞り込み / 重複統合）。黙って絞らない。
- **更新が全体中止になった場合も、`凡例` の「状態」行に理由が残る**（例: 個人情報の混入検知）。
  例外は外に投げないので、GASのトリガーが連続失敗で自動停止することはない。
- **1タブの書き込みが失敗しても、他タブは更新される**。失敗したタブ名は
  `凡例` タブの「状態」行と実行ログ・Slackに出る。**「状態」が『正常』でなければ、
  名指しされたタブの数字は古い**ので使わない。
  （2026-07-28 に、列名変更で1タブが例外→他タブが古いまま無言で残る事故が起きたため）

## 触るときの注意

- **列を足すときは個人情報にならないかを必ず検討する**。出力列は `AGENCY_SHARE_COLUMNS` の
  許可リストだけで、書き込み直前に元データの個人情報が混ざっていないか1セルずつ検査している
  （混入を検知したら**1行も書かずに中止**する）。
- 変更したら `node scripts/check-agency-share.mjs` を実行する（`release-pre-check.sh` にも入っている）。
  GASを模したスタブ上で `syncAgencyShare()` を丸ごと1回まわし、個人情報が出ないことを検査する。
- **ソルト `AGENCY_SHARE_SALT` を変えない**（過去の `lead_id` と繋がらなくなる）。
